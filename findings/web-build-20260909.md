# The web build over WebTransport — what it costs, measured

**2026-09-09.** Prompted by the operator: *"people dont wanna download
gates. take an assessment of what we need to do for the web build using
QUIC."* A measurement and a plan, not a law. Every number below carries the
command that produced it; re-run them rather than trusting this file.

Nothing here is a decision. Two of the items are the operator's alone (§6).

---

## 0 · The headline, before any of the detail

**We already speak WebTransport, and the server needs no change at all.**
The native client's transport is not "QUIC we could wrap for browsers" — it
is literally the browser's own API surface, one crate down:

| `crates/client/src/lib.rs` | browser equivalent |
|---|---|
| `endpoint.connect(&url)` :470 | `new WebTransport(url)` |
| `connection.open_bi()` :475 | `.createBidirectionalStream()` |
| `dg_conn.receive_datagram()` :588 | `.datagrams.readable` |
| `connection.send_datagram()` | `.datagrams.writable` |

And the certificate posture is already the browser's
(`crates/server/src/net.rs:365-381`, comment verbatim): *"A PUBLIC shard
serves a real certificate chain and browsers trust it outright; the dev flow
self-signs for loopback and the page passes the hash below through
`serverCertificateHashes`."* The P-256 / 14-day self-signed rules
`NETCODE.md` §2.2 enforces are **WebTransport spec rules written for
browsers** — that doc says so itself.

So the wire, the handshake, the cert rules and the shard-list URL shape are
all already browser-shaped. **The entire cost is on the client side.**

## 1 · What builds for wasm today — measured, not assumed

Three of six crates are already clean, and one of them was proven this
morning rather than remembered:

```
rustup target list --installed                    # wasm32-unknown-unknown present
cargo build -p client-core --release --target wasm32-unknown-unknown
#   Finished `release` profile [optimized] target(s) in 12.59s
```

`client-core` — `ClientCore`, the predictor, the interpolator, the clock —
compiles to wasm clean, first try, no edits. It depends on nothing but
`sim-core` and `protocol` (`crates/client-core/Cargo.toml`), and those two
already build to wasm on **every CI pass** and are diffed byte-for-byte
against native (`ci/gates.sh:200-215`, wall 1's own enforcement).

That is the whole game-logic half of the client, already portable, already
gated. It is worth stating plainly because it inverts the usual shape of
this question: the risky part of a browser port is normally "does the
simulation agree with the server", and here that is not merely solved, it is
a wall with a gate that has never been allowed to go red.

`wasm-bindgen 0.2.126`, `web-sys 0.3.103` and `js-sys 0.3.103` are **already
in `Cargo.lock`** — they arrive through Bevy 0.18.1 / wgpu 27 / winit 0.30's
own web backends. The renderer's dependency graph already contains its
browser path.

## 2 · What blocks, in the order the compiler hits it

```
cargo build -p client --release --target wasm32-unknown-unknown
#   error: This wasm target is unsupported by mio. If using Tokio, disable the net feature.
```

It dies on the **first dependency**, before reaching one line of our code.
The blockers, each with what it costs:

1. **tokio (`net`/`rt-multi-thread`) → mio.** Hard compile error. Used in
   six files: `lib.rs` (12 refs), `render/menu.rs` (9), `render/boot.rs`
   (4), `render/hub.rs` (4), `main.rs` (2). In the render trio it is only
   the thread that runs the connect future — on web that is
   `wasm_bindgen_futures::spawn_local`.
2. **wtransport / quinn.** No wasm target and never will have one: quinn
   owns a UDP socket, and a page has none. Replaced by `web-sys`'s
   `WebTransport`, not ported.
3. **`basis-universal` — and the first diagnosis here was wrong. Corrected
   the same day, by finishing the spike instead of stopping at the first
   error.** The opening symptom is real:
   ```
   clang++ --target=wasm32-unknown-unknown ... pvpngreader.cpp
   fatal error: 'stdlib.h' file not found
   ```
   and it reads as "no libc sysroot for this target", which is true and is
   **not the blocker**. Feeding it a real sysroot walks the error forward
   three times rather than fixing it — `stdlib.h` resolves, then
   `'algorithm'` is missing (libc++ lives at a per-target path,
   `include/wasm32-wasi/c++/v1`), then `<wasi/api.h> is only supported on
   WASI platforms` (compile the C++ as `--target=wasm32-wasi` while Rust
   stays `wasm32-unknown-unknown`), and only then does the real one appear:

   ```
   .../wasm32-wasi/setjmp.h:13:2: error: Setjmp/longjmp support requires
   Exception handling support, which is not yet standardized
       — compiling vendor/basis_universal/encoder/jpgd.cpp
   ```

   **`jpgd.cpp` is a JPEG decoder, and it is in the ENCODER.** `build.rs`
   compiles the encoder sources unconditionally and the crate publishes **no
   features at all** to turn them off. The client only ever *transcodes*.

   ⚠ **Two corrections, 2026-09-10, both read off the registry copy.** The
   count is **seventeen** at `:23-39`, not eighteen — the eighteenth
   encoder-side source is `vendor/encoding_wrapper.cpp` at `:42`, and only
   `:40`/`:41` are the transcoder. And the bigger one: **"a build-list change"
   understates it, so do not scope the work off that sentence.** The safe
   wrapper's `transcoder_init()` calls `sys::basisu_encoder_init()`
   (`basis-universal-0.3.1/src/transcoding/mod.rs:32`), which lives in the
   encoder, so a transcoder-only fork does not LINK on any target without a
   shim; `src/lib.rs:24` compiles `pub mod encoding` unconditionally, whose
   `image_init`/`image_clear` must also be satisfied; and the resulting module
   imports four `wasi_snapshot_preview1` functions that wasm-bindgen's
   `--target web` glue does not supply.

   So the transcoder was never the problem, and it builds — measured:
   ```
   clang++ -O3 --target=wasm32-wasi --sysroot=<wasi-sdk-24>/share/wasi-sysroot \
     -isystem .../include/wasm32-wasi/c++/v1 -isystem .../include/wasm32-wasi \
     --std=c++11 -fno-exceptions -DBASISD_SUPPORT_KTX2_ZSTD=0 \
     -c vendor/basis_universal/transcoder/basisu_transcoder.cpp
   # exit 0 — an 802 KB object file
   ```

   **The fix is therefore a build-list change, not a sysroot hunt**: a
   patched `basis-universal-sys` that compiles `transcoder/` only on wasm.
   Mechanical, contained, and it drops the encoder's PNG reader and JPEG
   decoder — dead weight in a game client on any target.

   Do not "solve" this by dropping the format: VRAM matters *more* in a tab,
   not less, and the whole reason that path exists is
   `crates/client/Cargo.toml`'s measurement that twelve props at three 2048²
   maps is ~600 MB of texture uncompressed.

   ⚠ **The lesson is the repo's own and it was re-learned here:** the first
   error a toolchain prints is the first thing it tripped over, not the
   thing that is wrong. Four errors deep, the diagnosis inverted — from "the
   transcoder needs a sysroot" to "the transcoder is fine and the encoder
   should never have been compiled." Stopping at error one would have put a
   wrong sentence in a plan somebody else executed.
4. **`ureq` (the shard list).** Blocking sockets. On web it is `fetch`, and
   `shardlist.rs`'s parser is already unconditional and already tested —
   only the fetch call moves.
5. **`elo_overlay.rs` + `discord.rs`.** Unix sockets and named pipes, 14
   call sites. **Neither can exist in a page**, and `elo_overlay.rs` is
   vendored byte-for-byte and must not be edited here (`CLAUDE.md`
   §vendored). Web identity is a different door — see §5.
6. **Filesystem, ~21 sites** clustered in `config.rs` (settings),
   `report.rs` (F7 bug report), `render/shot.rs` (screenshots),
   `ui/refusals.rs`. All small, all `localStorage` / a download shim.

## 3 · The seam is genuinely small, and that is the finding

The transport does **not** leak into the renderer. Measured:

```
grep -rln wtransport crates/client/src/     # lib.rs, args.rs, shardlist.rs
grep -n wtransport crates/client/src/args.rs crates/client/src/shardlist.rs
#   4 hits, ALL doc comments
```

So `wtransport` is confined to `lib.rs` alone. And what the renderer is
allowed to know about a connection is four methods
(`crates/client/src/lib.rs`):

```
pub fn client_endpoint(..)   :194
pub async fn connect(..)     :459
pub fn closed(&self)         :640
pub fn send_action(&self)    :656
pub fn pump(&mut self, dt_ms) -> Frame  :672
```

`grep -rn "Session\b" crates/client/src/render/*.rs` returns **five** sites,
two of which are comments. A browser transport has to satisfy that surface
and nothing else. `pump` is already a synchronous per-frame drain of a
bounded ring (`drain_datagram`, :423), which is exactly the shape a browser
`ReadableStream` reader wants to feed.

This is not luck. It is `RENDER.md` §1's rule — *Bevy draws, it does not
decide* — paying out somewhere nobody was aiming it.

## 4 · The two things that are actually hard

**4.1 · Threads, and it is a hosting decision.** `render/terrain_mesh.rs`
moved chunk meshing onto `AsyncComputeTaskPool` (:1053) precisely so the
frame would stop paying for it. On wasm **without** cross-origin isolation
there is no `SharedArrayBuffer`, Bevy's pools execute inline, and the work
lands back on the frame. What that costs, from `findings/client-frame-20260819.md`:

| work | native, per unit |
|---|---|
| `heightfield`, near chunk 65² @ 1 m | **5.153 ms** |
| `terrain::clutter_fill`, one 16 m tile | 1.006 ms |
| `water::stream`, a walking snap | 0.965 ms |

⚠ **Three things are wrong with that sum and only one of them is the digits.**
(a) They do not reproduce across boxes — two containers on this commit read
1.0–1.33× below them, and normalising each row by its own run's
`terrain::height` control makes the two agree within 7%. (b) **The three rows
never land on one frame**: `CHUNK_BUILDS_PER_FRAME = 1`,
`CLUTTER_FILLS_PER_FRAME = 1`, and `water::stream` fires under once a second at
a walk — so "~7.1 ms" is a worst-case coincidence presented as a budget, and no
re-measurement repairs that. (c) It omits the far mesh (`FAR_N = 257`, one
`pool.spawn`, ~138 ms measured), the largest single unit by roughly 20×.

**Do not re-run these and paste new digits** — the per-tap control itself
varies 380↔449 ns across containers, so the next box will not reproduce them
either. What the shape needs is a control row as a divisor, a sentence saying
the rows do not coincide, the far mesh added, and the honest admission that the
number actually wanted here is **wasm-in-a-tab, which nobody has measured**.

~7.1 ms of a 16.6 ms frame at 60 Hz, **before** wasm's own penalty on scalar
float code, and `CHUNK_BUILDS_PER_FRAME` is already 1.

⚠ **This paragraph prescribed COOP/COEP headers plus an atomics-enabled build,
and that fix does not exist at this Bevy version** (measured 2026-09-10, in the
registry copy). Bevy 0.18 loses threading at three **arch-keyed** compile-time
sites, none of which cross-origin isolation or `-Ctarget-feature=+atomics` can
flip, because neither changes `target_arch`:

| site | what it keys on |
|---|---|
| `bevy_tasks-0.18.1/src/lib.rs:21` | `multi_threaded` alias is `all(not(target_arch = "wasm32"), …)` |
| `bevy_ecs-0.18.1/src/schedule/executor/mod.rs:54-61` | `ExecutorKind::default()` is `SingleThreaded` on wasm32 |
| `bevy_internal-0.18.1/src/default_plugins.rs:50` | `PipelinedRenderingPlugin` gated off |

Our wasm graph already resolves `bevy_tasks`'s `multi_threaded` feature and it
is inert. So the 5.153 ms lands on the main thread **either way**, and the
streaming re-budget is unconditional rather than contingent on a hosting
decision. Do not spend an operator act on the headers for this reason. The
hosting question stays open for the ones that are real — the certificate path,
CORS, and a CSP that today blocks WebAssembly on the obvious origin (§6).

**4.2 · The download is not obviously smaller, and this is the honest half.**

```
du -sh assets/          # 92M   (82M of it assets/models/)
git ls-files -z assets/ | xargs -0 du -cb | tail -1   # 95,636,864 tracked
```

A Bevy wasm binary is tens of MB on top of that. **A web build does not beat
a 124 MB depot on bytes** — it beats it on *ceremony*: no installer, no
launcher, no platform depot, no OS trust prompt, and above all it can put a
player in the world while the rest streams. `render/loading.rs` already
draws the world as it streams in, which is the mechanism that makes this
work and it is already built. The pitch is **click and you are in**, not
"smaller". Anyone selling it internally as a size win will be wrong by
measurement in week one.

## 5 · Identity, which is a design question and not a port

`elo_overlay.rs` reaches a *local* launcher over a *local* socket, deliberately
so no key is ever in the game process (`CLAUDE.md` §vendored). A page has no
local launcher. So a web player is either a guest, or authenticates by some
route that does not exist yet — a browser wallet, or an elo web session. That
is a platform question, it is upstream of this repo, and **it should not be
allowed to block a guest-playable web build**: `Session::connect` already
"connects as a guest, which is what a declined prompt or an absent launcher
should do rather than failing the connection" (`lib.rs:457`). The absent
launcher case is already the web case, already handled.

⚠ One caveat that is not hypothetical: an `require_auth` shard answers
`REFUSE_AUTH` to a guest, and per `CLAUDE.md`'s vendoring trap that lands
looking like a bad signature. A web player hitting a locked shard must get a
message that says *this shard needs an account*, not a login failure.

## 6 · The collision — and it is the decision that has to come first

**`NOW.md` §0wt proposes dropping the HTTP/3 layer** and `NETCODE.md` §2.2
argues it: *"That layer now has no user, and it is not free."* The case is
real — the one remotely-triggerable panic we have ever pinned around lives in
that layer (#317), it is why we depend on a git rev of an unreleased crate,
and it costs a session-id prefix against the 1,100-byte datagram budget.

**A browser cannot open a raw QUIC connection.** WebTransport over HTTP/3 is
the only path a page has. So:

> **Dropping the HTTP/3 layer permanently forecloses the web build.**
> Doing the web build retires §0wt and makes the wtransport pin permanent.

These are mutually exclusive and both are flag-days. `NETCODE.md` §2.2 says
the layer "has no user" — **that premise is exactly what this assessment
puts back in question.** Neither doc is wrong; they were written before the
question was asked. This is an operator call and nothing should be built
against either branch until it is spoken.

If the web build is chosen, §0wt should be struck rather than deferred, and
`NETCODE.md` §2.2's "no user" paragraph corrected in the same commit — a
stale argument for deleting the thing we depend on is the exact drift
`CLAUDE.md`'s ⚠ about dead citations is about.

## 7 · What a plan looks like, if it is spoken

Ordered so each step is independently landable and green.

1. **A `Transport` trait behind `Session`.** Native impl is today's
   wtransport code, moved and not rewritten. No behaviour change, no wire
   change, gates green — this is the only step worth doing *before* the
   decision in §6, because it is a tidy-up that pays for itself either way.
2. **Split the client crate's platform floor.** `tokio`/`wtransport`/`ureq`
   behind a `native` feature; `fs` sites behind a small storage trait.
   Target: `cargo build -p client --target wasm32-unknown-unknown` reaches
   *our* code before it errors. That milestone is a gate.
3. **A `basis-universal-sys` patched to build `transcoder/` only** (§2.3).
   Done as a spike already: the transcoder compiles to wasm clean, and the
   encoder — which we never call — is what refuses. Needs a fork or a
   `[patch.crates.io]` entry plus the wasi-sdk sysroot flags in a
   `.cargo/config.toml`. Standalone; nothing else waits on it.
4. **The web transport**, `web-sys::WebTransport` against the trait from
   step 1. `crates/client-core/tests/wire.rs` is the gate that already
   exists for this half.
5. **Bevy on the web**: WebGL2 first (reach), WebGPU behind the existing
   quality ladder (`render/quality.rs` is already the right shape for it).
6. **Asset streaming and the COOP/COEP call** (§4.1, §4.2).

Steps 1–3 are the honest scoping spike: they answer every remaining unknown
without committing to the port.

## 8 · What this note does not claim

- No estimate of the wasm binary's size — nothing here built one.
- Bevy 0.18 on wasm was **not** run. Its web backends are in our lock file;
  that is evidence they exist, not that our 65k-line render path works under
  them. Step 5 is where that is found out, and it is the largest unknown left.
- No claim that any of this is wanted. §6 is unspoken and this note is
  research, not a queue.

## 10 · The platform audit (2026-09-09, later the same day)

Seven agents mapped the client's platform surface — six dimensions plus a
critic told to verify their `file:line` claims rather than trust them. ~440
sites. What follows is only what CHANGES the plan; the maps themselves are in
the workflow transcript.

### 10.1 · The critic's headline, and it is aimed at this document

> The riskiest assumption is **that the remaining wasm blockers all live in
> dependencies** — that once tokio and wtransport are cfg'd out, the compiler
> reaches and clears our code. […] The whole payoff rests on Bevy 0.18 +
> wgpu 27 + winit compiling and rendering this game in a browser, and nobody
> has run that build. […] the cheap way to retire this is a spike, not a
> plan — which is the lesson the assessment's own §2.3 already paid for and
> then did not apply to itself.

Fair, and acted on: §2 framed the failure as *"it dies on the first
dependency, before reaching one line of our code"*, and §1's only real
measurement was `client-core`, which depends on two path crates and nothing
else — **it proves the sim ports and proves nothing about the client.**
§8 did say Bevy-on-wasm was the largest unknown; it should have been the
first thing run, not the last thing listed.

**✅ RUN, AND IT PASSES — the assumption is retired.** A throwaway crate
(`bevy 0.18` with Gates' own feature set *minus* `basis-universal`, plus
`getrandom/wasm_js`, one `App::new().add_plugins(DefaultPlugins)`):

```
RUSTFLAGS='--cfg getrandom_backend="wasm_js"' \
  cargo build --release --target wasm32-unknown-unknown
#   Compiling bevy_audio v0.18.1 / bevy_gilrs v0.18.1 / bevy_anti_alias v0.18.1
#   Compiling bevy v0.18.1 … Finished `release` in 8m 12s   → exit 0
#   249 rlibs, bevyweb.wasm = 28 MB
```

Four things worth carrying:

- **`DefaultPlugins` builds unmodified** — no `default-features = false`
  needed. `bevy_audio` and `bevy_gilrs`, the two this repo has repeatedly
  eyed for trimming, both compile for wasm. So the trim is still a trim, not
  a prerequisite.
- **`getrandom` needs the RUSTFLAGS cfg and nothing else.** §10.2 item 4 is
  confirmed as a build-invocation fact; with it, 0.3.4 compiles.
- **28 MB is a pre-`wasm-opt`, pre-compression number** on `lto = "thin"`,
  and it is the artifact size, not the wire size. It does not yet include our
  65k lines of client. Treat it as the floor of a real measurement, not an
  estimate of the download — §4.2's honesty applies to this number too, and
  nobody should quote it as "the web build is 28 MB" until one is built.
- **It proves the graph compiles, NOT that the game renders.** No canvas, no
  surface, no frame — `bevy_render` initialising against a real WebGL2/WebGPU
  context in a browser is a separate question this does not answer. What it
  retires is the fear that the dependency stack refuses the target outright,
  which was the thing that could have made the whole project impossible.

### 10.2 · Four corrections to §2, verified against the tree

1. **The mio blocker is not ours.** `crates/client/Cargo.toml:433` asks for
   `rt-multi-thread, macros, time, io-util` — **no `net`**. mio arrives via
   wtransport → quinn's `runtime-tokio` = `["tokio/time","tokio/rt",
   "tokio/net"]`. Deleting our tokio line would not have moved it. But
   `rt-multi-thread` is independently a hard `compile_error!` on
   `target_family="wasm"` (tokio-1.53.1/src/lib.rs:467-479), so both go.
2. **`tokio/sync` is undeclared and load-bearing.** All 24 channel sites are
   wasm-supported and port untouched — but the feature reaches us *only*
   through quinn today. The wasm build removes wtransport and 24 sites fail
   with *"could not find `sync` in `tokio`"*, which reads as a code problem
   and is a manifest problem. **Declare it in the same commit as the split.**
3. **`tokio/time` compiles on wasm and PANICS.** It is not on tokio's refused
   list, so a future edit adding it back is green and dies at runtime. The
   reason has to be written as *panics*, not *disallowed*.
4. **`getrandom` ≥0.3 refuses `wasm32-unknown-unknown` by default** and needs
   both the `wasm_js` feature and `--cfg getrandom_backend="wasm_js"` in
   RUSTFLAGS — a build-invocation fact, not a manifest one. It arrives
   through `uuid` ← bevy_reflect/bevy_asset/bevy_animation/bevy_scene/
   bevy_ui/bevy_picking, so the render build cannot avoid it.

### 10.3 · The design call, and it is better than §7 step 1 assumed

**Make the trait synchronous and leave `connect` a free cfg-selected `async
fn`.** `Session`'s whole per-frame surface already refuses to await on
purpose (`lib.rs:669-671`), so no lane method needs `async` — which kills
`async-trait` *and* the real hazard: `rt.0.spawn` (`menu.rs:1348`) requires a
`Send` future and `wasm_bindgen_futures::spawn_local` must not have one, and
an async trait method cannot express "Send on one target, not the other".

**✅ Built 2026-09-09, and the seam measured SMALLER than the design
predicted: `Wire` has ONE method.** `crates/client/src/net/` now holds the
trait and the lane plumbing; `net/native.rs` is 38 lines. Walking every field
of a connected `Session`, exactly one call touches the transport — the
per-frame `send_datagram`. Everything else was *already* portable and nobody
had noticed: the reliable C→S lane is a `tokio::sync::mpsc::Sender`, both
inbound lanes are drained by free functions over an `mpsc::Receiver` and a
`Mutex<DgRing>`, and closed-ness is derived from those two drains. `sync` is
wasm-supported, so a web transport fills the *same* ring from a
`ReadableStream` and pushes events into the *same* channel.

`Session`'s definition now names no transport type at all — the cfg-selected
`wire: net::ActiveWire` is its only platform-bearing field — and `wtransport`
survives in `lib.rs` only inside `client_endpoint` and `connect`, which is
exactly the half the next slice takes. A concrete cfg-selected type, not
`Box<dyn Wire>` and not a generic: a trait object could not take the
`impl FnMut` drains and would allocate on a hot path, and a generic would leak
a type parameter into `render::Net` and every signature naming a session.

⚠ **One thing this did NOT do, found while reading rather than by a gate**:
`pump` sends `input_buf[..len]` with **no clamp against the live path MTU**,
where `CLAUDE.md`'s trap list says to clamp every send against
`max_datagram_size()` and is explicit that the ceiling outlived the browser.
`DATAGRAM_BUDGET_BYTES = 1100` sits under the 1,200 B QUIC floor so it is not
biting today, but the rule is unenforced and a browser is where the *silent*
form of that failure lived. Not fixed here — it is a behaviour change, not a
refactor — and `Wire` deliberately has no `max_datagram_size` yet, because an
unused trait method is a promise nothing keeps.

The pure half of the handshake is ~85 lines of which **six** touch the
transport. It must not be copied — and there is evidence for that beyond
principle: a second copy already exists at `server/src/net.rs:1917-2019`.

⚠ **But it has NOT diverged by accident, and the transport map was wrong to
call it a defect and propose unifying it first.** The client's `sign` is
`FnOnce(&str,&str,u64)` and the server's is `FnOnce(&[u8])`, and
`lib.rs:461-465` documents the client's shape as *the fix* — the launcher
composes every word, which is what stops a game smuggling a sentence into a
signature. Unifying them would re-introduce a login bug this repo has already
paid for. The critic caught this; it is the most expensive thing in the audit.

### 10.4 · What the wasm build hits AFTER the dependencies — all ours

- **`elo_overlay.rs`: seven `cfg(unix)`/`cfg(windows)` pairs with no third
  arm** (:51-58, :513, :526, :543, :569) — and the file is vendored and
  unpatchable here. The fix needs no vendored byte: one `#[cfg(not(target_arch
  = "wasm32"))]` on the `#[path] mod` at `elo.rs:132-133`. It works because
  the re-exported names have **zero call sites outside `elo.rs`**, and the
  sha256 pin uses `include_bytes!` — which reads the file rather than
  compiling it, so the drift gate survives on every target.
- **`discord.rs`: four more of the same** (:783, :785, :813, :822). Ours to
  edit, so it gets a third arm rather than a cfg-out — `render/presence.rs`
  imports seven names from it and the pure half carries a test suite.
- **`[[bin]] client` has no `required-features`** (`Cargo.toml:49-51`) and
  `src/bin/soundbank.rs` is an undeclared autobin. Both drag `#[tokio::main]`
  and wtransport back regardless of what the library does.
- **`limit_frames` is a runtime panic, not a compile error** — `Instant::now`
  + `thread::sleep`, registered unconditionally in `Last`
  (`render/mod.rs:794`, `settings.rs:1115-1121`). **Worth fixing whether or
  not the web build ships**: it is a latent panic wearing a target triple, and
  `bevy_platform::time::Instant` (already in the lock) is the swap.
- **`Session` is built by value on the stack** (`lib.rs:615-632`, including
  `input_buf: [u8; DATAGRAM_BUDGET_BYTES]` and a whole `ClientCore`).

## 11 · What landed (2026-09-10) — and the three places the plan was wrong

The remaining steps of §10.6 are built, plus the transport itself and an entry
module. `ci/gates.sh` carries a browser-client gate. **Nothing here has been
opened in a browser**, and §11.5 is that boundary drawn honestly.

### 11.1 · The split is by TARGET, not by feature — except where it cannot be

§7 step 2 and §10.6 step 5 both said "behind a `native` feature", and that is
right for exactly one thing and wrong for the rest. The distinction that
matters, found while writing it:

- **A cargo feature models a builder's choice.** There is no choice about
  `tokio`'s runtime, `ureq`'s blocking socket or quinn's UDP socket in a tab —
  the platform decides, and a feature is a flag somebody can pass wrong.
  Those moved to `[target.'cfg(not(target_arch = "wasm32"))'.dependencies]`,
  where no invocation can get them wrong and `--no-default-features` is not
  required to be remembered.
- **A feature is still needed for one job**: `[[bin]] required-features`, the
  only lever cargo gives for *do not build this binary here*. Both player
  binaries open a terminal or an OS window; without the requirement they
  compile for wasm32 and die inside `#[tokio::main]`.

So `native = ["dep:wtransport"]` and everything else is a target table. Two
mechanisms that must agree is a convention, so `lib.rs` carries a
`compile_error!` pair proving exactly one transport is selected — one arm of
which is the mistake somebody will actually make (`cargo build -p client
--target wasm32-unknown-unknown` with defaults on, which without it spends two
minutes and dies in 48 errors inside `mio`).

`tokio` is declared twice, `sync` in the base table and the four runtime
features in the target one; cargo unions them, so a native build sees exactly
the five it saw before. Probed before landing: cargo accepts a feature naming
an **optional dependency that lives only in a target table** (`render =
["dep:ureq"]` with `ureq` under `cfg(not(wasm32))`), and on wasm the feature
enables nothing.

### 11.2 · The framing adapter is the piece §10.6 named, and it is pure

`net/frame.rs`: `FrameBuf<const N: usize>` — a `[u8; 2]` header and a `[u8; N]`
body, no `Vec`, no growth, so **wall 4 is satisfied by construction rather
than by a cap check**. A declared length above `N` is refused at the header
before a byte is copied, and the session ends; there is no truncate-and-
continue arm because the reliable lane drops nothing.

Written with no transport type, no `async` and no target cfg **so that it
could be gated on a box with no browser** — which is the whole point, because
the bug in this thing lives in the chunking. `crates/client/tests/framing.rs`
feeds one byte stream in every chunking from whole down to one byte at a time
and requires the same frames out of all of them.

**Four mutants run, four caught** (`CLAUDE.md`'s rule, and the reason to state
it here rather than to imply it): `from_le_bytes` → `from_be_bytes`;
`declared > N` → `declared >= N`; `Ok((used, ..))` → `Ok((chunk.len(), ..))`;
and `take()` no longer resetting `hdr_len`. The third is the one worth naming
twice — it is the residue bug, it costs nothing on a stream that happens to
arrive one frame per chunk, and in play it would present as **a rare missing
event at join**.

The residue is why `FrameReader::rekey` exists. `read_exact` stops on the byte
it was asked for; a browser read returns whatever arrived, so the chunk that
completes `welcome` can perfectly well carry the first event frames — and the
handshake reads at `MAX_STREAM_MSG_BYTES` while the event lane reads at
`MAX_EVENT_MSG_BYTES`, which are different `const N` and therefore different
types. Building a fresh reader after the handshake, the obvious thing to
write, drops those bytes silently.

### 11.3 · The MTU clamp, finally, at the one call site that can hold it

`CLAUDE.md`'s trap list has said since the first browser client that *a
browser datagram write over `maxDatagramSize` silently succeeds and sends
nothing*, and §10.3 found `pump` had no clamp and deliberately left it (a
behaviour change, not a refactor). `WebWire::send_datagram` has one: the live
value per send, because path MTU moves; **refused rather than truncated**,
because every payload here is an encoded message whose decoder checks its
length; and **counted**, so a lane that has quietly stopped reaching the shard
is a number somebody can read rather than a player who cannot move.

⚠ **"a number somebody can read" was false when it was written, twice on this
page, and it is true as of 2026-09-10.** A whole-repo grep for `over_mtu` and
`backpressured` returned the two declarations, their initialisers and the two
halves of their own increments — nothing else. `Session.wire` is private with
no accessor and `client-web`'s whole surface was `join`/`pump`/`snapshots`/
`player_id`/`seed`/`closed`, so no target could read either number. A promise a
doc makes and the tree does not keep is the exact ⚠ `CLAUDE.md` is about, and
this page made it. `Session::wire_counts` and `Gates.refused` are the reader;
the desktop side still has no counter to read, and `net/native.rs` discarding
wtransport's `Err` — `TooLarge` included — is what it owes.

`Session::pump` still has none. That is safe today only because
`DATAGRAM_BUDGET_BYTES = 1100` sits under the 1,200-byte QUIC floor — a
constant holding a rule up, which is exactly what the trap list exists to warn
about, and it is still open.

1. **`elo.rs` needed more than the `mod` line.** §10.4's fix — one

## 13 · Identity, built (2026-09-10) — and §5 was right about the wrong thing

§5 called identity *"a design question and not a port"* and argued it must not
block a guest-playable web build. The operator settled it the other way and the
argument was better: a guest shard is a second process to run, a second world to
wipe, and a population that cannot be told apart. So the wallet landed first.

### 13.1 · The one asymmetry, and it is forced

The desktop inversion — three inert values out, the LAUNCHER writes every word —
cannot hold in a page, because `window.ethereum` has no `prove` verb. A wallet
signs text or nothing. So `net::handshake::Proof::message` composes the SIWE
text **in Rust**, through the same `protocol::siwe_message` the shard calls in
`server::auth::verify`, and the page receives a finished string.

What replaces the launcher's guarantee is what every SIWE dapp relies on: the
wallet renders the message before the human approves it, and the shard
recomputes, so a page that composed something else gets `WrongSigner` rather
than a login. The thing that must never be written is a JavaScript copy of the
message — a second implementation of a byte-exact format whose only symptom on
drift is every login failing while both sides look right alone.

### 13.2 · Three things measured rather than assumed

- **The elo launcher's relay is closed to this, on purpose.**
  `meter/signin.py::_guard_ask_text` refuses any relayed text containing
  *"wants you to sign in with your ethereum account"* — *"the launcher composes
  those itself… so no page can write one"*. Our message contains that phrase by
  construction (`protocol/src/auth.rs`). Extension wallet only; opening that
  door is a platform security decision nobody has asked for.
- **EIP-55 had to move, not be copied.** `siwe_message` takes the checksummed
  address as text and its doc always said the caller needs keccak — true of one
  caller (the shard) until a browser became the second. `checksum_hex` left
  `server::auth` for `protocol::Address::to_checksum_hex`, and `protocol` took
  `tiny-keccak` (no_std, no transitive deps, already in the lock).
- **The live shard is `PROTO_VER` 61 against this tree's 62.** Version is
  checked before auth, so none of this is reachable at `game.elopros.com:61234`
  until it is redeployed. Not a defect — an ordering fact worth writing down
  before somebody tests against production and reads `REFUSE_VERSION` as a
  wallet bug.

### 13.3 · The mutant that survived, and what it cost to notice

`the_two_step_path_and_the_composition_agree` compares the auth frame built by
`auth_for` against the one built by `proof_wanted` + `auth_frame` — and **both
sides call `auth_frame`**, so a mutant that made it discard the signature and
always encode a guest passed every assertion in the file. That is `CLAUDE.md`'s
`lattice.rs` entry verbatim, committed by somebody who had read it an hour
earlier, in the same slice that cites it. The gate decodes the frame through
`protocol::decode_auth` now and asserts the address and signature that went in.

Run the mutants. Three were run here; one of the three was worthless until it
was.

`personal_sign` has never been called. Every claim above is a code-tier gate or

## 14 · Somebody opened it (2026-09-11) — and the first frame panicked

§13.4 said *"`personal_sign` has never been called"*. It has now. A headless

```
127.0.0.1 wants you to sign in with your Ethereum account:
0x3DA8D322CB2435dA26E9C9fEE670f9fB7Fe74E49          <- EIP-55 casing, live
Prove your identity to play gates. …
Nonce: 32e21130086c84d4f99a4218c719e61493fd1bf21ea304ff658c73229fbc6d94
```

Measured in the same run: a guest is refused and reads *"this shard needs a
signed identity - connect a wallet in this browser and join again"*; the same
shard admits the signed join; **60 snapshots in 2 s** against a 30 Hz shard;
holding W moved the body **4.10 m**; and `over_mtu` / `backpressured` /
`dropped` are all 0.

**None of it is a gate and none of it should be** — `CLAUDE.md` is explicit

and is not committed.

### 14.1 · What opening it found, which is the whole argument for opening it

The join succeeded and then the page froze forever, reporting a completed join:

```
gates: panic: min > max, or either was NaN. min = 0.005849999999976717, max = -0.005849999999976717
```

`ClientCore::advance` spent the **raw** `dt_ms` on three things before handing
it to `ClientClock::advance`, which is the only layer that clamped. One of the
three is `max_step = PLAYOUT_SLEW_PER_S * dt_ms / 1000.0`, used as
`clamp(-max_step, max_step)` — negative `max_step` is `min > max`, which
`f64::clamp` panics on, and a panic in wasm is the module gone.

**A negative frame time is normal in a browser and impossible natively.**
`requestAnimationFrame` is handed the timestamp of the frame's *start*, which
can precede a `performance.now()` read taken moments earlier, so the first
frame's delta is routinely below zero. Every native caller derives `dt` from a
monotonic clock. So this was unreachable by every gate in the repo, on the one
code path both clients share, and it killed the browser on frame one every
time.

Fixed as `clock::sane_dt` — one function both layers call, NaN included, with
the clamp moved to the top of `advance` — rather than a `Math.max(0, …)` in the
page, because a caller that has to remember a guard is a caller that will
forget it. `core.rs`'s
`a_frame_time_below_zero_is_survived_rather_than_panicked_on` is proven red
under the old body: it reproduces the identical panic.

### 14.2 · What is still not claimed

No **real** wallet has been used — the stub signs with a fixed key through the
same `personal_sign` shape, which proves our bytes and not MetaMask's UI. The
MetaMask SIWE domain-match behaviour that argues for hosting on
`game.elopros.com` is still unverified. And there is still no renderer: this is
the headless pump, so "in the world" means the state arrived, not that anything
was drawn.

## 15 · The renderer in a browser (2026-09-11/12) — three walls that declined politely, then a count

`client-web` builds an `App` now (`Gates::play(canvas)` — the session is
handed to Bevy in a tab, `WorldId` and `Net` inserted before `add_plugins`,
the page's own `requestAnimationFrame` loop deleted rather than left dormant
because `pump` drains the core's rings destructively), `ci/build_web.sh`
stages `assets/` from `git ls-files` and refuses to walk, and the first
browser boots of it hit four walls in a row. Each one was found by opening
the page, none by a gate, and that is the argument §14 already made.

### 15.1 · Three "not loaded" log lines that were each fatal

WebGL2 allows **zero storage buffers in the fragment stage**, and three Bevy
features each want one two hops away:

| feature | how it asked | what it cost to remove |
|---|---|---|
| `ScreenSpaceAmbientOcclusion` | `#[require(DepthPrepass, NormalPrepass)]`; their mesh-view layout binds a storage buffer | `quality::tier` clamps the browser to `Low`, and `rig::setup` inserts the component conditionally — the rig spawns the DEFAULT tier, so it would have inserted before `apply` ran |
| `Atmosphere` | `mesh_view_layout_atmosphere` | conditional insert; the browser gets `fill.rs`'s hemisphere and no aerial haze — a visibly flatter sky, written at the site |
| (`DepthPrepass`/`NormalPrepass` themselves) | the layout label walked down one term at a time: `…_depth_normal_atmosphere` → `…_atmosphere` → gone | nothing further |

**The trap is that each declines politely.** `AtmospherePlugin not loaded.
GPU lacks support for compute shaders` and `ScreenSpaceAmbientOcclusionPlugin
not loaded` are both in the console and both read as handled. A plugin
declining does not remove the COMPONENT, and the component is what shapes the
mesh-view layout. A log line saying a feature is off is not evidence the
feature is out of the way. `bevy/webgpu` is not a switch to flip for any of
this: every WebGL workaround in the engine is spelled `not(feature =
"webgpu")`, so enabling it disables all of them with no runtime fallback.

### 15.2 · The fourth wall was a count, and the count is summed

With the storage buffers gone the pipeline layout was refused for a different
reason: `max_sampled_textures_per_shader_stage` is **16** on WebGL2
(`downlevel_webgl2_defaults`, and it is `GL_MAX_TEXTURE_IMAGE_UNITS`
underneath). `ground_splat.wgsl` declared exactly sixteen `texture_2d`s. The
material's own doc called textures "the cheap axis" and samplers the one with
a floor under it, which was right about every desktop adapter and wrong about
the one adapter that IS the floor.

Two things about the limit that took reading wgpu to learn. It is counted
**per stage across every bind group in the pipeline layout** — wgpu merges a
`BindingTypeMaxCountValidator` over all the layouts at
`create_pipeline_layout` — so the view's shadow and environment maps and
`StandardMaterial`'s six slots are in the same 16 as ours; the error's 22 was
the material group alone (6 + 16). And a `texture_2d_array` is ONE binding
however many layers it holds, sampled with the same filter, chain and
anisotropy as the standalone texture — a layer is not a lossy substitute for
a texture, it is the same texels behind one more index.

So the sixteen became **three** (`textures::GroundArrays`): albedo (4 layers,
`Rgba8UnormSrgb`, 1024²), normal (4, `Rgba8Unorm`, 1024²), and roughness
with AO behind it (8, `Rgba8Unorm`, 512² — the two families are the same
size and format, so they share; `AO_LAYER0 = 4`). Not four, because the view
plus `StandardMaterial` on WebGL2 is already ~12 and four would sit at the
line; not two, because roughness/AO are 512² and albedo/normal 1024², and
upsampling one into the other's alpha channel is a resample the desktop would
see. One shader for both targets, no web variant.

### 15.3 · The stacking, and the one-frame window it had to avoid

`textures::stack_ground` builds the arrays out of `GroundMaps` after
`mipmap::drain`, one family a frame (the albedo array is ~22 MB of texels
copied; `CLAUDE.md`'s stream-in rule is that a frame pays for one of those),
`RENDER_WORLD` only, and then **removes `GroundMaps`** — sixteen sources whose
every texel is also in an array are ~56 MB of VRAM held for nobody
(`PropMaps` shares the `rock` handles, so those stay).

**When to build is the hazard, not how.** An image is in `Assets<Image>` one
frame before its `Added` event reaches `mipmap::enqueue`, so "loaded and not
pending" is true for exactly one frame on an image that is about to get a
chain — a builder keyed on that stacks sixteen single-level layers with every
gate green, and the chains `mipmap.rs` took a slice to build end up in the
sources and in nothing that is drawn. `textures::layer_ready` is therefore
derived from `mipmap::wants` — the one predicate that cannot disagree with
`drain`, because `drain` calls it — and a non-power-of-two image the pass
will never touch is ready as it is, or the ground would wait forever on it.

`terrain_mesh::stream` takes `Option<Res<GroundArrays>>`: the far mesh's
~190 ms build is still queued on the first frame, and what waits on the
arrays is the LANDING, so `far_done` — the flag that ends the loading screen —
keeps meaning "the island is up and drawable" rather than "up but
untextured". `tests/ground_async.rs` inserts the arrays from frame 0 and
every claim it makes is still about the meshes.

### 15.5 · What gates it, and the two mutants that were run

- **`tests/ground_arrays.rs`** (new, 5 legs): the stack is layer-major and

so the ground pipeline itself — the one the arrays exist for — has not yet
been created in a browser; what §15.4 proves is the arrays on the desktop

```
In Device::create_render_pipeline, label = 'pbr_opaque_mesh_pipeline'
  Error matching ShaderStages(VERTEX) shader requirements against the pipeline
    Shader global ResourceBinding { group: 0, binding: 14 } is not available in the pipeline layout
      Buffer structure size 1024, added to one element of an unbound array, if it's the
      last field, ended up greater than the given `min_binding_size`, which is 16
```

Binding 14 is `visibility_ranges`, the LOD table `VisibilityRange` dithers
by, and every tree here carries one (`tree::TreeLod` — the near pair and the
far hull). With no storage buffers the WGSL side becomes `var<uniform>
visibility_ranges: array<vec4<f32>, 64>` — 1,024 bytes — while Bevy's layout
entry keeps the storage case's `min_binding_size = Vec4::min_size()` (16) for
both, and wgpu refuses the pipeline. Only a pipeline with
`VISIBILITY_RANGE_DITHER` touches the binding, which is why Bevy's own WebGL2
examples do not hit it and a forest does. No 0.18 point release fixes it
(`cargo update --dry-run`: 0.18.1 is the latest). The fix is ours and
wasm-only: swap a tree's LOD by a system on that target rather than by the
component — the same `TreeLod` distances, no crossfade.

Also logged, and not fatal: `no definition in scope for identifier:
bevy_pbr::prepass_utils::prepass_depth`. Bevy's `forward_decal.wgsl` — the
bullet marks, `decal.rs` — reads the depth prepass, and the browser camera
has had none since SSAO's `#[require]` went (§15.1). A decal material that
fails to compile is a mark not drawn, not a crash; `DepthPrepass` on its own
is a texture and not a storage buffer, so it is worth putting back alone. And
47 glTF loads fail as `format requires transcoding: Uastc(Rgb)` — the
models-are-absent item, unchanged.

`ci/build_web.sh` built `client-web` with `--release`, the native profile,

|---|---|---|---|---|---|---|
| `--release` (lto thin, opt 3) | 73.4 MB | — | — | — | 77.0 MB | 13.77 MB |

### 17.1 · The sky is baked into the deck

`sky.rs`'s cloud cubemap keeps every clear texel at ZERO on purpose — the
atmosphere composites the deck onto its own sky — and a browser has no
atmosphere (§15.1), so §15.7's frame was cumulus on black. On wasm32 the
deck now carries a clear sky behind the clouds (`sky::backdrop_at`): the

the horizon is `HORIZON_GAIN` brighter and `HORIZON_DESAT` greyer along an

over nothing. The desktop's bake is byte-unchanged and `tests/sky.rs` holds
both bakes to each other natively — identical wherever a cloud is opaque,
exactly the backdrop wherever the desktop's texel is zero — because a gate
that only ran the `cfg!`'d arm would be green over a wrong browser sky. The
premultiplied-over-black mutant reddens it.

In the frame: a slate-blue gradient with the same clouds, where the corner

### 17.2 · Models draw, through a build-time variant

The UASTC transcoder is C++ and is not in the wasm build, so the browser had

### 17.3 · A material created before its chain landed kept the one-level upload

`bevy_pbr` prepares a material's bind group once and never again on

forever. The ground was out of it by construction and the menu path by luck

### 17.4 · The page is the menu, and the surface follows the window

`Screen::Menu` was a dead end on wasm32 (nothing draws it, and the `Session`
is one-shot) and `AppExit` a frozen canvas. `web::leave_to_page` on
`OnEnter(Menu)` and `web::exit_to_page` in `Last` call `window.gatesLeft
(status)` — the page stores the reason and reloads, and says it on the way
back in — or reload outright when no page installed the hook. Verified from
the loading screen's Escape (the one road to `Menu` that re-locks nothing,
§17.6): the page navigated and came back reading *"left while the world was
loading — press Play to go back in"*. ⚠ The reason names the SEED rather
than the shard, because `Gates::play` fills `Start::direct` with the seed;
the page knows the address and should hand it over.

The surface: `web::fit` scales the viewport in device pixels uniformly
under WebGL2's 2048 cap and the page stretches the canvas back over the
viewport with a CSS transform, because winit's `ResizeObserver` sizes the
backing store from the CSS box times `devicePixelRatio` and `offsetX` is in
the element's own space — a transform is invisible to both, a bigger box is
not. The scale override is `devicePixelRatio` itself; the first build's 1.0
drew a retina canvas at half size. Measured in the harness at 1920 × 1080,
DPR 2: CSS box 1024 × 576, `transform: scale(1.875)`, the rect 1920 × 1080.
**Probed rather than assumed** (`probe2.mjs`, headless Chromium 140): a
1024 × 576 canvas under `transform: scale(1.875)` — on the element or on a
wrapper, applied before observing — reports a device-pixel content box of
**1024 × 576** at DPR 1 and at DPR 2, while its bounding rect is 1920 ×
1080. The transform is invisible to the observer, which is the whole design.
⚠ Under Playwright's ratio emulation the observer reports CSS pixels
(1024 at "DPR 2", where a display would say 2048), so the emulated run's
numbers disagree with themselves — Bevy briefly held 4096 × 2304 before
`follow_viewport` corrected it to 2048 × 1152 in the same frame, and the
canvas attribute read 1920 × 1080 — and none of that is a display's
behaviour. The store's half is therefore proven by the probe and by
`tests/web.rs`, not by a headless frame; a retina display is `NOW.md`
§0web's first remaining item.

### 17.6 · Decals: two walls, stacked — and the pointer lock

`DepthPrepass` alone on the browser camera did what §15.6 hoped: the decal
shader compiled. The PIPELINE was then refused — *"the type given for group
3 binding 200 has a size of 4 … must have a size that is a multiple of 16"*
(`ForwardDecalMaterialExt`'s one `f32`, and WebGL2 has no
`BUFFER_BINDINGS_NOT_16_BYTE_ALIGNED`) — and a refused pipeline is a fatal
wgpu error, the module gone on the prewarm draw of the first mark, where the
compile failure had been a logged line. The prepass is off again and the
mark pool is empty on wasm32 (`decal::setup`); the fix is a 16-byte
extension with its own copy of `forward_decal.wgsl`, not carried yet. A wall
that declines politely can be standing in front of one that does not.

The pointer: the baseline's first look run panicked in winit's web runner
(`runner.rs:519 RefCell already borrowed`, then every frame) after a click on
the death screen that also engaged the pointer lock. Three later runs did
not — one clicking the same row, one with the lock FORCED from a page-side
`requestPointerLock()` inside the click so the grant did not depend on
Bevy's frame landing inside the activation window: locked, a 40-move drag
under it, released on Escape, zero panics. Mouse look turns the view (the
compass N 000° → W 280°). **Root-caused, and it was never a winit bug.**
A symbolized build put a name on the first trap — `std::alloc::rust_oom` —
and the page's `gatesWasm.memory.buffer.byteLength` read **4.15 GB**, the
32-bit ceiling: an allocation failed, `abort` is a bare `unreachable`, and
the trap unwound the JS stack through winit's handler with the runner's
`RefCell` borrowed, which is the panic every later frame reported. Eleven
runs with the heap sampled every two seconds pinned WHEN it grows: flat
at 570–720 MB through the world, a big view turn, a press that Bevy
answers with a lock the browser does not grant, and W — and **~75 MB/s the
moment the browser GRANTS the pointer lock**, motion or none (a press with
a page-side `requestPointerLock()`: 535 → 2832 MB in 30 s, then the
ceiling). `web::heap_report` split the heap: assets and entities barely
moved while `Messages<MouseMotion>`, `<CursorMoved>` and
`<RawWinitWindowEvent>` held **842,562 messages in one frame**.

The source is the browser: a bare page (`probe3.mjs`) under pointer lock in
headless Chromium 140 receives **~30,000 `pointerrawupdate` events a second
with the pointer stationary** (113,448 in 4 s; 1 without the lock), which
Chromium coalesces into the `pointermove` events winit reads through
`getCoalescedEvents()`, and which Bevy then buffers without a bound. On
hardware a stationary mouse produces no updates and a moving one produces
its polling rate, so the flood is the test environment's — but the shape is
`CLAUDE.md` wall 4's exactly, an unbounded queue on a client-driven path,
and it is winit's and Bevy's rather than ours to cap. Every run that died
had taken the lock (a death-row click, a resume, a respawn, each inside the
key's activation window); every run that lived had asked and been refused.
The harness now avoids a granted lock on purpose, and says so.
